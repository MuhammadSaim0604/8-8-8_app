# DayBlocks — 8-8-8 App: Complete Functional Specification

> **Purpose of this document:** A platform-agnostic, implementation-neutral description of every feature, screen, and behavior in the DayBlocks app. Any developer reading this can rebuild it in Kotlin/Java, Flutter, SwiftUI, Expo React Native, or any other technology. Nothing here is about code — it's all about *what the app does and why*.

---

## 1. The Core Concept: The 8-8-8 Principle

A full day has 24 hours. DayBlocks divides those 24 hours into three equal **blocks** of 8 hours each:

| Block | Name | Purpose |
|-------|------|---------|
| 🌙 Sleep | Sleep & Recovery | Rest, sleep, recovery |
| 💼 Work | Work & Learning | Focus, growth, productivity |
| 🧘 Personal | Personal Life | Health, family, hobbies |

**The app does not tell you when to do things.** It helps you *plan how much time* you want to spend in each block and then *track how long* you actually spend doing each activity. The philosophy is: "your day, your time, your rules."

Each block has a hard cap of **exactly 8 hours (480 minutes)**. The sum of all task durations inside a block cannot exceed 480 minutes. This constraint is the heart of the app.

## 2. Core Data Model

### 2.1 Task

A **Task** is the fundamental unit of the app. It represents one activity the user wants to track.

| Field | Type | Description |
|-------|------|-------------|
| `id` | unique string | Auto-generated, never changes |
| `blockId` | enum: sleep / work / personal | Which 8-hour block this task belongs to |
| `name` | string | User-provided label (e.g. "Deep Work", "Evening Run") |
| `durationMinutes` | integer, 1–479 | How many minutes the user *plans* to spend on this task |
| `color` | hex color string | A color chosen from a palette of 10 options |
| `createdAt` | timestamp | When the task was created |

**Constraints on tasks:**
- Minimum duration: 1 minute
- Maximum duration per task: 479 minutes (7h 59m) — never 8 hours or more
- Maximum total duration across all tasks in one block: 480 minutes

### 2.2 Timer State

At any given moment, **at most one task can be running** across the entire app. The timer state tracks that single running task:

| Field | Type | Description |
|-------|------|-------------|
| `taskId` | string | Which task is currently running |
| `blockId` | enum | Which block the running task belongs to |
| `startedAt` | timestamp (ms) | When the current run session began |
| `accumulatedMs` | integer | Milliseconds already counted from previous paused sessions *today* |

**When the timer is null:** no task is running.

### 2.3 Task Progress

A separate map of `taskId → accumulatedMs` tracks tasks that have been **paused** (they have some time accumulated but are not currently running). When a task is paused, its elapsed time is saved here. When it resumes, it picks up from where it left off. This map is cleared when the day resets.

### 2.4 History Entry

Every time the user **stops** a task (not pauses — stops), and the task was running for more than 5 seconds, a history entry is saved:

| Field | Type | Description |
|-------|------|-------------|
| `id` | unique string | Auto-generated |
| `taskId` | string | Which task was tracked |
| `taskName` | string | Name of the task at time of stopping |
| `blockId` | enum | Which block |
| `blockName` | string | Human-readable block name |
| `elapsedMs` | integer | How many milliseconds were tracked in this session |
| `date` | string (YYYY-MM-DD) | Calendar date of the session |
| `stoppedAt` | timestamp | When the session ended |

History accumulates indefinitely across days. It powers all statistics.

### 2.5 Settings

| Field | Default | Description |
|-------|---------|-------------|
| `notificationsEnabled` | true | Whether to show the persistent notification |
| `dailyResetHour` | 0 (midnight) | When the day resets (progress clears) |

### 2.6 App State Summary

The complete app state that must persist across restarts:
- List of tasks
- Active timer state (or null)
- Task progress map (paused tasks)
- History (all completed sessions)
- Settings
- Last reset date (YYYY-MM-DD)

**All state is local to the device.** There is no server, no account, no sync.

## 3. Daily Reset Logic

Every day has a "reset" moment (by default: midnight). When this moment passes:
1. The active timer is stopped/cleared (any running task is interrupted)
2. All task progress (paused tasks' accumulated time) is wiped
3. The `lastResetDate` is updated to today

**Tasks themselves are never deleted by the reset** — they persist across days. Only the *progress towards those tasks* resets each day.

The reset is checked periodically (e.g., every minute) while the app is open. When the app is launched, if the saved `lastResetDate` is not today, a reset is applied automatically before showing the UI.

## 4. Navigation Structure

The app has two navigation levels:

**Tab Bar (always visible at bottom):**
1. **Home** — Dashboard overview
2. **Tasks** — Full task list, grouped by block
3. **Stats** — Statistics and history
4. **Settings** — Permissions and data management

**Stack screens (pushed on top):**
- **Block Detail** — Deep dive into one specific block (navigated from Home or Tasks)
- **Running Task** — Fullscreen timer view (navigated from MiniPlayer or Home "Now Playing" card)

**Persistent overlays (sit above the tab bar but below the stack):**
- **MiniPlayer** — A slim bar that slides up from above the tab bar whenever a task is running or paused
- **Floating Quick Button (FAB)** — A circular button (bottom-right) that opens the QuickMenuOverlay

## 5. Screen-by-Screen Specification

### 5.1 Home Screen (Dashboard)

**Purpose:** At-a-glance overview of the entire day.

**Header:**
- A time-of-day greeting ("Good Morning", "Good Afternoon", "Good Evening", "Good Night") with an icon appropriate to the time

Three block cards, one per block (Sleep, Work, Personal), each showing:

- Only shown when a task is actively running.
- Shows the task name, block icon, and block name.

**Tip Card (conditional):**

## 6. Reusable UI Components

### 6.1 Task Card

Used in Block Detail, Tasks screen, and QuickMenuOverlay. Shows a single task.

**Layout:**
- Left edge: a 3px vertical accent bar in the task's color
- Task name (bold)
- A pulsing dot before the name when this task is currently running
- Duration chip (clock icon + formatted time, e.g., "1h 30m")
- Elapsed time (shown only if > 0): formatted as MM:SS or H:MM:SS
- Remaining time (shown only when this task is running)
- Progress bar (shown only if any progress > 0): thin horizontal bar, filled proportionally, colored with task color
- Right side: Edit icon (pencil), Delete icon (trash)
- Far right: Play/Pause button (a 42×42 rounded square)
  - Shows pause icon + task color background when this task is running
  - Shows play icon + neutral background when idle or paused
  - If **another** task is running and user taps play on this task → shows Switch Task confirmation sheet

**States:**
- **Idle:** No elapsed time shown; play button neutral
- **Running:** Pulsing dot, elapsed + remaining shown, progress bar filling in real time, pause button shown
- **Paused:** Elapsed time shown (frozen), play button shows play icon

### 6.2 MiniPlayer

Appears **above the tab bar** and slides up from below when a task starts. Slides back down when a task is stopped.

**Layout:**
- Full-width card with left border in task color
- Thin progress bar along the top of the card (elapsed/total), colored in task color
- Task name (with colored dot) + block name + elapsed / total time
- ⏸/▶ button (pause/resume)
- ⏹ button (stop)

**Behavior:**
- Tapping the card body (not a button) navigates to the Running Task screen
- Uses a spring animation to slide in from below and a timing animation to slide out
- Updates elapsed time every second while running
- Remains visible even when the task is paused (showing paused state)
- Disappears only after the task is stopped

### 6.3 Floating Quick Button (FAB)

Always visible in the bottom-right corner of the tab screens.

**Appearance:**
- Circular button (52×52) with a grid icon
- Blue background
- Bottom position adjusts upward when MiniPlayer is visible (so the FAB floats above MiniPlayer)
- A pulsing ring animation plays around the button when a task is actively running
- Scale-in spring animation on first render

**Action:** Opens the QuickMenuOverlay sheet.

### 6.4 QuickMenuOverlay

A large bottom sheet (86% of screen height) that can be opened from the FAB. Provides quick task management without leaving the current screen.

**Header:**
- App icon + "LifeBlocks" title + "8-8-8 DASHBOARD" subtitle
- Close (chevron-down) button

**Search Bar:**
- Real-time text filter across all tasks; filters by task name (case-insensitive)
- Shows matching tasks per block; hides entire block sections if no matches
- If nothing matches: shows a "No tasks match" empty state

**Three Block Sections:**
Each block (Sleep, Work, Personal) has:
- Block icon + block label (e.g., "SLEEP BLOCK") in block's accent color
- Task count for that block
- Each task shown as a QuickMenu task card:
  - Task name + duration on line 1
  - ▶/⏸ toggle button + ⏹ stop button (stop only visible if task has any progress)
  - Progress bar (colored)
  - Elapsed time / total time on line 3
  - Live tick: if this task is running, elapsed time increments every second inside the overlay
  - Active dot (colored) when running

**Design:** Uses a distinct dark color palette (separate from the main app) with per-block accent colors: green for Sleep, blue for Work, orange for Personal.

### 6.5 Circular Progress Ring

SVG-based circular progress indicator used throughout the app. Parameters:
- **Size** (diameter in px)
- **Stroke width**
- **Progress** (0.0 to 1.0, can exceed 1.0 for overtime scenarios)
- **Color** (stroke color)
- **Track color** (background ring color)
- Optional **gradient end** color for multi-color rings

Renders a track ring and a progress arc. Children can be placed inside the ring center (e.g., a percentage label).

## 7. Bottom Sheet Components

All sheets use animated slide-up from the bottom with a dark translucent backdrop. Tapping the backdrop dismisses the sheet.

### 7.1 Add Task Sheet (also used for Edit Task)

**Triggered by:** "+ Add" button on any block, the FAB in Block Detail, the "Add" button in Tasks screen.

**In edit mode:** Pre-fills all fields with the existing task's data.

**Fields:**

*Task Name:*
- Text input, auto-focused when sheet opens
- Placeholder: "e.g. Deep Work, Evening Run…"

*Duration (Wheel Picker):*
- Two side-by-side scroll wheels: Hours (0–7) and Minutes (0–59)
- iOS-style snap-scroll wheels where the selected value is centered and highlighted
- A colon separator between the wheels
- Below the wheels: a summary row showing total minutes (e.g., "1h 30m · 90 min total")
- A colored badge on the right:
  - Green + "Xm left" when duration fits in the block
  - Orange + "+Xm over" when duration exceeds available block capacity
  - Red + "≥8h!" when the hard cap is hit
- Hard cap hint: "Max 7h 59m per task (under 8 hours)"

*Color Grid:*
- 10 color swatches in a grid, each 40×40 circular
- Selected swatch shows a checkmark and a border highlight

**Validation:**
- Empty name → error "Please enter a task name"
- Zero duration → error "Duration must be at least 1 minute"
- Duration ≥ 480 → error "Maximum task duration is 7h 59m"
- Duration exceeds block free time → error "Only Xm free in this block. Need to free Ym first." + a "Free up time" button that opens the Reduce Time Sheet while keeping this sheet open underneath

**Save button:** disabled (dimmed) until both name and duration are valid. On success: haptic feedback + closes sheet.

### 7.2 Reduce Time Sheet

**Purpose:** Helps the user free up capacity in a block that is full (or would be overfull after adding a planned task).

**Shows:** List of all tasks in the block. Each task shows its name and current duration.

**Actions per task:** User can reduce a task's duration via a -15m / -30m button (or similar controls), or remove a task entirely.

**Shows:** How many minutes are needed to free up (passed from the Add Task sheet context when block is overfull).

### 7.3 Delete Confirm Sheet

**Triggered by:** Trash icon on any TaskCard.

**Content:**
- Task name + duration (confirms which task will be deleted)
- "Cancel" and "Delete" buttons

**Effect:** Permanently removes the task. If the deleted task was currently running, the timer stops. Task progress for this task is also cleared.

### 7.4 Switch Task Sheet

**Triggered by:** Tapping the play button on a task that is *not* the currently running task, when *another* task is already running.

**Content:**
- Confirms switching: "Are you sure you want to switch tasks? The current task will be paused."
- Shows which task the user is switching to
- "Cancel" and "Switch" buttons

**Effect on confirm:** The currently running task is automatically paused (its progress is saved). The new task starts immediately.

## 8. Timer System

### 8.1 Starting a Task

When the user taps play on a task:
1. If another task is running → show Switch Task confirmation sheet
2. If no task is running → immediately start the timer
3. The timer state records: task ID, block ID, current timestamp (startedAt), and any accumulated milliseconds from previous paused sessions today

### 8.2 Elapsed Time Calculation

**While running:** `elapsed = accumulatedMs + (now - startedAt)`

This calculation is done in real time on the device — there is no server clock. The UI updates this every 250ms (on the Running Task screen) or every 1 second (on MiniPlayer and TaskCard).

### 8.3 Pausing a Task

1. Calculate elapsed: `accumulated + (now - startedAt)`
2. Save this value into the `taskProgress` map under the task's ID
3. Set timer state to null (no task running)
4. The task card shows the frozen elapsed time; play button available to resume

### 8.4 Resuming a Task

1. Retrieve accumulated milliseconds from `taskProgress`
2. Remove the entry from `taskProgress` (to avoid double-counting)
3. Create a new timer state: same task ID, current timestamp, retrieved accumulatedMs

### 8.5 Stopping a Task

1. Calculate final elapsed: `accumulated + (now - startedAt)`
2. If elapsed > 5 seconds AND task exists → create a HistoryEntry and add it to history
3. Clear timer state to null
4. Remove task from `taskProgress` (no more accumulated progress)
5. The task card returns to idle state (no elapsed shown if no history)

### 8.6 Switching Tasks

Starting a task when another is already running automatically pauses the current one (saves its accumulated time to `taskProgress`), then starts the new task.

### 8.7 Overtime

When elapsed time exceeds the task's budgeted duration:
- The progress ring reaches 100% and continues filling (clipped at 100% for display)
- The "remaining" counter shows "+X:XX" in red (negative remaining = overtime)
- An "Overtime" badge appears on the Running Task screen
- The ring color shifts toward red/orange
- The app does NOT automatically stop the task — the user must stop it manually

## 9. Notification System

### 9.1 Persistent Notification (All Platforms)

The app shows a persistent notification in the device's notification tray at all times (when permission is granted). This notification:
- **Cannot be dismissed** by swiping (set as ongoing/non-dismissible on Android)
- Updates in real time (every second) while a task is running
- Updates immediately when the timer state changes

**Notification Content:**

| State | Title | Body |
|-------|-------|------|
| Idle (no task) | "DayBlocks" | "8-8-8 Dashboard · tap to open" |
| Running | "⏱ TaskName" | "MM:SS elapsed · tap to open" |
| Paused | "⏸ TaskName" | "Paused · tap to resume" |

**Action Buttons:**

| State | Buttons |
|-------|---------|
| Running | ⏸ Pause, ⏹ Stop |
| Paused | ▶ Resume, ⏹ Stop |
| Idle | (no buttons) |

**Action button behavior:** Tapping Pause/Resume/Stop from the notification tray performs the exact same action as if done inside the app — state updates immediately.

**On Android:** The notification uses a dedicated low-priority channel ("DayBlocks"), shows no sound/vibration, has `ongoing: true` and `autoDismiss: false`.

### 9.2 Notification Channel Setup (Android)

A notification channel named "DayBlocks" with `LOW` importance is created on first launch. Action categories ("RUNNING" and "PAUSED") are pre-registered with their buttons so they're ready when permission is granted.

### 9.3 Notification Permission Flow

- The app does NOT show a permission prompt automatically on launch.
- The user sees the permission status in Settings.
- If undetermined: an "Allow" button triggers the system permission dialog.
- If denied: a "Settings" button deep-links to the device's app notification settings.

## 10. Floating Bubble System (Android Only)

The floating bubble is a native Android foreground service that draws a small draggable circle over all other apps using the system overlay API (`SYSTEM_ALERT_WINDOW` / `TYPE_APPLICATION_OVERLAY`).

### 10.1 What It Is

When a task is running or paused and the user leaves the DayBlocks app, a small circular bubble remains floating over whatever app the user opens. The bubble shows:
- The elapsed time (counting up in real time when running)
- The first ~9 characters of the task name
- A dimmed/translucent appearance when paused (alpha ~0.55)
- A glow ring around it when active

### 10.2 When the Bubble Appears

- Appears when a task starts (or is resumed from pause) **AND** the user has granted the "Draw over other apps" permission
- The bubble is removed (but the service continues) when the task is stopped

### 10.3 Bubble Interactions

**Drag:** The bubble can be dragged anywhere on the screen. It stays where dropped.

**Tap:** Tapping the bubble (without dragging) opens the DayBlocks app.

### 10.4 Notification from the Bubble Service

The foreground service (which is required to keep the bubble alive) also shows its own Android notification with:
- The task name in the title
- Block name + elapsed time in the body
- Three action buttons: **⏸ Pause** (or **▶ Resume**), **⏹ Stop**, **Hide Bubble** (or **Show Bubble**)

The "Hide/Show Bubble" button allows the user to temporarily hide the overlay without stopping the timer.

### 10.5 Event Flow (Bubble ↔ App)

The bubble service and the app communicate via the Android broadcast system:
1. **App → Bubble:** When a task starts/pauses/stops/updates, the app sends a broadcast with the new task name, block name, elapsed seconds, and paused state.
2. **Bubble → App:** When the user taps Pause/Resume/Stop in the bubble's notification, the bubble sends a broadcast back to the app. The app then updates its state accordingly (same effect as if the button was tapped in-app).

This means the bubble and the in-app UI stay in sync: pausing from the notification tray, the bubble's notification, or the in-app controls all result in identical state changes.

### 10.6 Bubble Lifecycle

| Trigger | Effect |
|---------|--------|
| Task starts | Start service; create bubble view; start 1-second tick |
| Task pauses | Update bubble to paused state; tick stops; notification updates |
| Task resumes | Update bubble to running state; tick resumes |
| Task stops | Remove bubble view; service goes to idle state (but keeps its notification running) |
| App calls stopBubble | Service is destroyed entirely |
| User taps "Hide Bubble" in notification | Bubble view is hidden (set to gone) but service remains |
| User taps "Show Bubble" in notification | Bubble view becomes visible again |

### 10.7 Permission Requirements (Android)

- `FOREGROUND_SERVICE` — to run as a foreground service
- `SYSTEM_ALERT_WINDOW` (a.k.a. "Draw over other apps") — to create the overlay window
- `POST_NOTIFICATIONS` (Android 13+) — to show the foreground service notification

The `SYSTEM_ALERT_WINDOW` permission is **not granted automatically** — the user must go to Settings and enable "Draw over other apps" for the DayBlocks app. The Settings screen guides them there.

## 11. Data Persistence

All data is stored **locally on the device** with no network connection required.

**Storage key:** `@lifeblocks_v1`

**What is stored:** The complete app state as JSON — tasks, timer state, task progress, history, settings, last reset date.

**When data is saved:** Immediately after every state change.

**When data is loaded:** On app startup. If the stored `lastResetDate` is not today, the reset logic runs before the UI is shown.

**Migration:** When loading older data, the app checks for missing fields (e.g., history array, settings object) and fills them with defaults.

---

## 12. App Initialization Flow

1. Fonts are loaded (Inter family: 400/500/600/700)
2. Splash screen is shown until fonts finish loading
3. Notification channel and action categories are set up
4. Stored app data is loaded from local storage
5. If today is a new day (different from `lastResetDate`), reset is applied
6. State is initialized; splash screen hides; app is shown
7. The persistent notification is posted/updated immediately after load
8. The floating bubble service (if applicable) is started/updated based on timer state

## 13. State Update → Side Effects Chain

Whenever any of the following change, side effects are triggered:

| Trigger | Side Effects |
|---------|--------------|
| Task starts | Update notification (title = task name, buttons = Pause/Stop); Start/update bubble service |
| Task pauses | Update notification (title = ⏸ task, buttons = Resume/Stop); Update bubble to paused state |
| Task stops | Update notification (back to idle); Remove bubble view |
| Timer ticks (every second while running) | Update notification body (elapsed time); Update bubble timer display |
| App comes to foreground | Re-post notification (OS may have dismissed it) |
| New day (midnight check) | Reset timer + progress; Update notification |
| Settings change | Update notification behavior |

## 14. Block Capacity Management

### Adding Tasks When Block Is Full

When a block reaches 480 minutes total:
1. The "Add Task" button changes to "Free up time" (red)
2. The Add Task sheet shows an error and a "Free up time" button
3. The Reduce Time Sheet opens, allowing the user to shorten or delete existing tasks
4. Only after freeing enough minutes can the new task be saved

### The Overflow Indicator

In the Add Task sheet, as the user adjusts the duration wheels:
- The colored badge next to the total shows remaining capacity in the block
- If the new duration would exceed available space: badge shows "+Xm over" in orange
- If it hits or exceeds 480: badge shows "≥8h!" in red
- The Save button is disabled in overflow state

## 18. Implementation Notes for Rebuilders

If you are rebuilding this app in any platform, here are the key engineering decisions to replicate:

1. **The timer is wall-clock based, not tick-based.** Elapsed = `accumulated + (nowTimestamp - startTimestamp)`. This survives app restarts, backgrounding, and phone restarts accurately.

2. **Only one running task globally.** There is no concept of "multiple timers." The entire app shares a single timer state.

3. **Pause saves accumulated time.** When paused, the accumulated milliseconds are stored separately so resuming is seamless.

4. **History is append-only.** Sessions are never edited after being saved. Statistics are always computed from the raw history array.

5. **The notification is a live timer.** When running, it updates every second. This requires either a foreground service (Android) or background task capability (iOS).

6. **The floating bubble is Android-only.** iOS does not have system overlay windows. On iOS, the persistent notification is the only background indicator.

7. **Block capacity is enforced at save time, not display time.** The UI shows warnings as the user adjusts duration, but the hard block happens on the Save button.

8. **The daily reset is date-based, not timer-based.** The app compares the stored reset date to today's date, not to a specific time — meaning if the user sets `dailyResetHour` to 6am, the reset date changes at 6am. (In the current implementation, reset hour is always midnight/0 but the field exists for future use.)

9. **Color is a user choice per task.** There is no automatic color assignment — the user picks from a fixed palette of 10 colors.

10. **The floating bubble service is an Android Foreground Service** with `foregroundServiceType="specialUse"`. It must show a notification to stay alive. The bubble view is added to the WindowManager with `TYPE_APPLICATION_OVERLAY`.
